**Timeline:**

**The Bug Mechanism:**
1. Models trained with window=5 features (pipeline.py:144-155)
2. Models expect features like `passing_yards_roll5`, `rushing_yards_roll5`
3. `_compute_rolling_stats_for_player()` in roster.py:124 defaults to window=3
4. Creates features with `_roll3` suffix that don't match model expectations
5. Default features in `_get_default_features()` use hardcoded `_roll5` keys (lines 256-275)
6. When features.update(rolling_stats) merges at line 450, roll3 keys don't overwrite roll5 defaults
7. Result: All players use position-typical roll5 defaults → identical predictions

**Evidence:**
- Diagnostic script output showing three QBs with vastly different actual stats (175.6, 247.6, 271.8) all receiving the same default value (250.0)

**Fix Required:**
Change default window parameter from 3 to 5 in:
- `_compute_rolling_stats_for_player(history_df, window=5)` (line 124)
- `_compute_volatility_for_player(history_df, window=5)` (line 172)
- No changes needed to function calls at lines 424, 425, 448, 449 (will use new default)

## Technical Notes

**Key Insight:**
The Python dict.update() method only adds new keys or overwrites existing keys with the same name. When you have:
```python
features = {"passing_yards_roll5": 250.0}  # defaults
rolling_stats = {"passing_yards_roll3": 175.6}  # computed
features.update(rolling_stats)
# Result: {"passing_yards_roll5": 250.0, "passing_yards_roll3": 175.6}
# Model only reads roll5 → gets default!
```

This is a simple key-mismatch bug, but with significant impact on prediction quality.

**Impact:**
This bug affects ALL predictions for ALL positions since Phase 19.1-02 (when rolling window was changed to 5). Every player prediction since then has been using position defaults instead of player-specific stats.
